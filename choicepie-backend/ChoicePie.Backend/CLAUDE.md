# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
dotnet build ChoicePie.Backend.sln          # build everything
dotnet test ChoicePie.Backend.sln           # run all test projects
dotnet run --project ChoicePie.Backend.WebApi   # run the API (http://localhost:5185)
docker compose up --build                   # containerized run (WebApi Dockerfile)
```

Test projects mirror every product project (`Domain.Tests`, `Application.Tests`, `Infrastructure.Tests`, `Shared.Kernel.Tests`, `Shared.Application.Tests`, `WebApi.Tests`). All use NUnit3; `Domain/Application/Infrastructure/Shared.*.Tests` additionally use NSubstitute + ExpectedObjects for unit tests. `WebApi.Tests` is the exception — it uses `Microsoft.AspNetCore.Mvc.Testing` (`WebApplicationFactory<Program>`, `Program` is `partial` for this reason) + `Testcontainers.PostgreSql` to spin up a real Postgres container and run true HTTP/DB integration tests (`CustomWebApplicationFactory.cs`), not mocks. In Development, Scalar API docs are served at `/api-docs`.

Runtime config is NOT in appsettings.json — the WebApi project uses user secrets. Required sections: `DatabaseConnections` (an **array** of `{ "Type": "NPGSQL", "ConnectionString": "..." }`; only the first entry is used and only `NPGSQL` is supported), `RedisConnection:ConnectionString`, and `Jwt:SigningKey` (the JWT HMAC signing key; `Jwt:Issuer`/`Jwt:Audience`/`Jwt:AccessTokenExpirationSeconds` have non-secret defaults in `appsettings.json`). `Cors:AllowedOrigins` (string array) also has non-secret defaults in `appsettings.json`.

Other config sections (all optional, defaults in `appsettings.json`; secrets belong in user secrets): `Smtp` (MailKit sender + `FrontendBaseUrl` for email links), `Google:ClientId`, `AiQuizGeneration` (`Provider` = `Anthropic`, `ApiKey`, `Model`), `CloudflareR2` (quiz cover/avatar uploads), `AdminBootstrap` (`Email`/`Name`/`Password` for seeding the first admin), `ForwardedHeaders` (`KnownProxies`/`KnownNetworks`, default loopback only — add the Nuxt BFF's IP/network in deployment or every user shares one rate-limit bucket), `RateLimiting` (`Auth`/`Email`/`Ai`/`Write`/`Global`, each `PermitLimit` + `WindowSeconds`), `Sentry` (`Dsn` empty = Sentry not registered at all, `TracesSampleRate`), `Serilog:MinimumLevel` (`Default` + `Override`; replaces the old `Logging:LogLevel` section), `LogOutput:Format` (`Text`/`Json`; empty = `Text` in Development, `Json` elsewhere).

## Architecture

.NET 10 / C# 14 Web API. Clean Architecture + DDD, MediatR, EF Core + PostgreSQL, HybridCache + Redis.

Projects split into two groups:

- **`ChoicePie.Backend.Shared.*`** — reusable framework code, where nearly all logic currently lives:
  - `Shared.Kernel` — domain primitives, no framework deps: `Entity<TId>`, `AuditableEntity<TId>` (audit columns + soft delete), `AppendOnlyAuditableEntity`, `AggregateRoot<TId>` (collects domain events), `ValueObject`, `Enumeration`, `DomainException`, `IRepository<T>`, `IUnitOfWork`, DI marker interfaces.
  - `Shared.Application` — MediatR contracts, `DomainEventNotification<T>`, `ICachingService`, paging contracts (`PagedResult`, `PaginationParameters`).
  - `Shared.Infrastructure.Persistence` — EF Core: `EfGenericRepository`, `EfUnitOfWork`, Npgsql registration, auditable-entity configurations.
  - `Shared.Infrastructure.Caching` — `HybridCachingService` over **FusionCache registered as `HybridCache`** (`.AsHybridCache()`): L1 memory, L2 Redis (key prefix `ChoicePie_`), and a Redis backplane that propagates `Remove`/`RemoveByTag` to other nodes' L1. Global defaults: 30 min TTL, fail-safe (max 2h, 1s factory soft timeout), Redis errors/timeouts fall through to the source. Only `HybridCacheEntryOptions` reach the adapter, so per-entry fail-safe tuning isn't possible through `ICachingService`.
  - `Shared.Infrastructure.Email` — `SmtpEmailSender` (MailKit, behind `IEmailSender`), `SmtpSettings`, `FrontendUrlProvider` (builds links in emails).
  - `Shared.Infrastructure.Security` — `Hashers/Argo2IdPasswordHasher` (Argon2id via Konscious.Security.Cryptography, 64MB/4 iterations/2-way parallelism, constant-time compare) and `Tokens/RefreshTokenGenerator` (32 random bytes as the raw token, SHA-256 hex digest persisted server-side).
  - `Shared.Hosting` — ASP.NET Core cross-cutting: `ApiResponse<T>` envelope (`Code`/`Status`/`Data`/`Message`), global exception handler chain (`DomainException` → `BadRequest` → default, via `IExceptionHandler` + ProblemDetails), Scalar/OpenAPI setup, custom JSON converters, Scrutor DI scanning, plus:
    - `RateLimiting/` — fixed-window limiter. Named policies `auth` / `email` / `ai` / `write` (`RateLimitPolicyNames`, applied with `[EnableRateLimiting(...)]` on endpoints) plus a global limiter; health paths are exempt. Partition key is the JWT `sub` when authenticated, else the client IP (`RateLimitPartitionKeyResolver`); `auth` always partitions by IP. Limits come from `RateLimiting:*`; rejections are written as the `ApiResponse` envelope with 429.
    - `Extensions/ChoicePieForwardedHeadersExtensions` — `X-Forwarded-For` is honored only from `ForwardedHeaders:KnownProxies`/`KnownNetworks`. `UseForwardedHeaders()` must stay first in the pipeline (before rate limiting).
    - `HealthChecks/` — `/health/live` (process only) and `/health/ready` (Redis via `DistributedCacheHealthCheck` + PostgreSQL DbContext check added in `Program.cs`); anonymous, outside `/api/v1`, no HTTPS redirect, JSON output without exception details.
    - `Monitoring/SentryConfiguration` — `AddChoicePieSentry()` registers Sentry only when `Sentry:Dsn` is set; `BeforeSend` drops expected exceptions (`DomainException`, validation, `InvalidOperationException`, cancellation) so only unexpected 5xx errors are reported. Error-level logs reach Sentry through the **Serilog Sentry sink** (`ConfigureSerilogSink`), not the MEL provider; `EnsureSdkInitialized` resolves `IHub` when the Serilog logger is built, because Sentry.AspNetCore otherwise initializes the SDK only on the first request and startup/background-service errors would be lost (`SerilogSentryWiringTests` guards this).
    - `Logging/` — Serilog replaces the MEL providers (`AddChoicePieSerilog()`, `preserveStaticLogger: true` so each host — including every node in multi-node tests — builds its own logger; app code keeps injecting `ILogger<T>`, Domain/Application never reference Serilog). Output is stdout only (one JSON object per line outside Development, via a `Serilog.Expressions` template so `@l` is always present and `@m` is plain text) for Grafana Alloy → Loki to collect; every event carries `Application`/`Environment`/`MachineName`/`Version` + W3C `TraceId`/`SpanId`. `UseChoicePieRequestLogging()` sits between `UseForwardedHeaders` and `UseExceptionHandler` and hands the middleware the host's Serilog `ILogger` (by default it writes to the static `Log.Logger`, which is the bootstrap logger here): one line per request with `RoutePattern`/`ClientIp`/`UserId`, `/health` skipped, 5xx logged as **Warning** (the exception itself is already an Error from `DefaultExceptionHandler` — logging Error here would open a second Sentry issue). `Program.cs` uses a plain (non-reloadable) bootstrap logger inside `try/catch/finally` so startup failures (migration, seeding) are logged. **Never log PII** — ids and `ClientIp` only, no email/name/token/password/body. Log format, label rules and an Alloy example: `docs/logging-loki.md`.
    - `Authorization/` — `ActiveMemberRequirement`/handler (see Auth flow) and `ActiveMemberAuthorizationResultHandler` (inactive member → 401 instead of 403).
- **Product slice** — `Domain`, `Application`, `Infrastructure`, `WebApi` (each has an `AssemblyReference` marker class used for assembly scanning). Dependency direction: `WebApi → Infrastructure → Application → Domain → Shared.Kernel`; each layer may also reference its matching `Shared.*` project. Never point an inner layer at an outer one.
  - **Aggregates** (`Domain/Aggregates/`): `Member` (end-user profile, separate from credentials; suspension, tier), `AuthAccount` (end-user login credentials — password + external OAuth identities — linked to a `Member`), `AdminUser` (admin-side profile/role), `AdminAuthAccount` (admin login credentials, mirrors `AuthAccount`), `RefreshToken` (hashed refresh-token record backing the JWT refresh flow), `PasswordResetToken` / `EmailVerificationToken` (hash-only, single-use tokens for the email flows), `MembershipTier` (member tier, drives the AI-generation daily quota), `AiUsageLog` (per-member AI generation usage), `Quiz` (quiz definition: questions, difficulty, status incl. `TakenDown`, cover image), `QuizAttempt` (one user's attempt at a `Quiz`), `QuizFavorite` (member bookmark), `CreatorFollow` (member follows creator), `Comment` (quiz comment, author-only edit/delete), `QuizReport` (member report of a quiz, resolved/dismissed by admin), `GameRoom` (live multiplayer game/session state machine backing `GameHub`, persisted directly in Redis via `RedisGameRoomRepository` — no HybridCache/L1, so every node reads the same state — not PostgreSQL), `GameSession` (durable historical record of a completed `GameRoom`). Application slices mirror these (`Application/<Feature>/` with Commands/Queries/Contracts/Dtos), plus `Account`, `AdminDashboard`, `AdminMembers`, `AdminQuizzes`, `AdminQuizReports`, `Uploads`.
  - **WebApi surface**: `Controllers/` (route `api/v{version}/...`; request DTOs live in matching `WebApi/Requests/<Feature>/` folders, bound directly as action parameters) — member side: `AuthController` (register/login/google/refresh/logout/forgot-password/reset-password/verify-email/resend-verification/me), `AccountController` (profile, avatar, password, Google link/unlink, delete), `MeController` (favorites, following, following quizzes), `CreatorsController` (profile, quizzes, follow), `QuizzesController` (CRUD, publish/archive, AI generation, tags, share, related, favorite, comments, report; `GET {id}` is anonymous), `QuizAttemptsController`, `GameSessionsController` (hosted/played history), `UploadsController` (quiz covers → Cloudflare R2); admin side: `AdminAuthController`, `AdminDashboardController`, `AdminMembersController`, `AdminMembershipTiersController`, `AdminQuizzesController`, `AdminQuizReportsController` (all `AdminOnly`). Write/auth/email/AI endpoints carry `[EnableRateLimiting]`. `Hubs/GameHub` (SignalR, `Hub<IGameHubClient>`, mapped at `/api/gamehub`) — authenticated Host-only methods (`CreateRoom`, `StartGame`, `SkipQuestion`, `PauseGame`, `RejoinRoom`, policy `MemberOnly`) plus anonymous methods (`JoinRoom` — returns player id + reconnect token, rejects duplicate nicknames case-insensitively; `RejoinAsPlayer` — rejoin with the reconnect token; `SubmitAnswer`; and `WatchRoom` for the bigscreen spectator — room group only, never the host group, not counted as a player); server→client events via `IGameHubClient` (`RoomCreated`, `PlayerJoined`, `PlayerLeft`, `PlayerDisconnected`, `PlayerReconnected`, `PauseStateChanged`, `HostConnectionChanged`, `AnswerProgress`, `GameStarted`, `QuestionStart`, `AnswerResult`, `QuestionEnd`, `GameEnd`, `RoomStateSync`). `OnDisconnectedAsync` dispatches `DisconnectHostCommand` (marks host offline, auto-pauses, broadcasts `PauseStateChanged` + `HostConnectionChanged(false)`) or `DisconnectPlayerCommand`; spectators are ignored. `RejoinRoom` is the `RejoinAsHostCommand` (host returns, broadcasts `HostConnectionChanged(true)`, replies `RoomStateSync`). Every command that rewrites an existing room implements `IGameRoomCommand`; `GameRoomLockBehavior` (registered in `Program.cs`) runs it inside a per-room `IDistributedLock` (`RedisDistributedLock`, SET NX + token, 15s lease), so concurrent answers/joins/reconnects on any node can't overwrite each other — a reflection test fails if a new room command forgets the marker. SignalR uses the Redis backplane (`AddStackExchangeRedis`, sharing the cache's `IConnectionMultiplexer`) so group broadcasts reach connections on other nodes; the frontend client still negotiates, so multi-node needs sticky sessions at the load balancer unless the client skips negotiation. `DomainExceptionHubFilter` translates `DomainException`s into `HubException`s for the hub, mirroring the WebApi exception-handler chain.
  - **Auth flow**: `JwtTokenBuilder` (`Infrastructure/Identity/`) builds the access token (HMAC-SHA256, `sub` + role claim). `WebApi/Extensions/AuthCookieExtensions.SetAuthCookies` also writes access + refresh tokens as `HttpOnly` cookies (`access_token` / `refresh_token`, `Path=/`; `Secure` outside Development; `SameSite=Lax`, or `SameSite=None` + `Secure` + `Domain` when `Auth:CookieDomain` is set for cross-subdomain deployments) in addition to the response body. The refresh/logout endpoints read the refresh token from the `X-Refresh-Token` header only, not the cookie. `WebApi/Extensions/JwtAuthenticationExtensions` reads the JWT from the `access_token` cookie via `OnMessageReceived` (falling back to the `Authorization: Bearer` header — which is how the Nuxt BFF calls REST endpoints), and the cookie flow authenticates the SignalR WebSocket handshake for `GameHub`. **Policies** (`WebApi/Extensions/AuthorizationPolicyExtensions`): `AdminOnly` (role claim) and `MemberOnly` (role claim **plus** `ActiveMemberRequirement` — the `sub` member must still exist, not be soft-deleted, not be suspended; checked by `IMemberActivityChecker`/`MemberActivityChecker`, cached per member for 60s with a 10s L1 and invalidated by `MemberAccountClosed`/`MemberSuspended`/`MemberUnsuspended` domain-event handlers; failure returns **401** via `ActiveMemberAuthorizationResultHandler` so the frontend's refresh-and-retry logs the user out). Invalidation reaches other nodes' L1 through the FusionCache backplane.
  - **AI quiz generation / web page fetching**: `QuizGenerationService` picks an `IQuizGenerationProvider` by `AiQuizGeneration:Provider` (`AnthropicQuizGenerationProvider`, a typed `HttpClient`). Input may be a URL: `ExternalServices/WebPages/WebPageContentFetcher` fetches it with SSRF protection (`WebPageUrlGuard`: http/https only, no userinfo, ports 80/443/8080/8443, no localhost/private/reserved IPs; `SsrfSafeConnector` re-checks resolved IPs at connect time), extracts text (`WebPageHtmlTextExtractor`, falling back to structured data via `WebPageStructuredDataExtractor`) and throws `WebPageRequiresJavaScriptException` for JS-only pages. **Caveat:** `WebPageContentFetcher` is registered in `Program.cs` as a typed client (`AddHttpClient<IWebPageContentFetcher, WebPageContentFetcher>().ConfigurePrimaryHttpMessageHandler(SsrfSafeConnector.CreateHandler)`) and deliberately does **not** implement a DI marker interface — Scrutor scanning would otherwise re-register it and bypass the SSRF handler. Do not add `IScopedDependency` etc. to it.

### Architectural principles

New code must follow **DDD** (aggregates own their invariants; model with the Shared.Kernel primitives — `AggregateRoot`, `ValueObject`, `Enumeration`; repositories only for aggregate roots), **Clean Architecture** (respect the dependency direction above; Domain stays framework-free; Use Cases live in Application as MediatR handlers), and **EDA** (state changes communicate via domain events raised on aggregates and dispatched through `EfUnitOfWork` — don't call other modules' services directly when an event fits). Apply established design patterns deliberately when they fit, and watch for code smells (long methods, large classes, primitive obsession, feature envy, etc.) when writing or reviewing code.

Local `dotnet-*` skills enforce these principles — invoke the matching skill when designing, implementing, or reviewing code in that area:

| Concern | Skill |
|---|---|
| DDD modeling / aggregate boundaries | `dotnet-ddd-skill` |
| Layering / dependency-direction review | `dotnet-clean-architecture-skill` |
| Command/Query separation (MediatR) | `dotnet-cqrs-skill` |
| Domain events / messaging | `dotnet-eda-skill` |
| Design pattern selection & review | `dotnet-design-pattern-detector-skill` |
| Code smell detection / refactoring | `dotnet-code-smell-detector-skill` |
| Full combined architecture review | `dotnet-architecture-review-suite-skill` |

**This project is developed with TDD.** When implementing any new class, method, or feature, invoke `dotnet-tdd-skill` and drive the work through the Red-Green-Refactor cycle — start from a failing test, don't write production code first. For hardening or reviewing already-written tests, use `dotnet-nunit-unit-test-skill` (NUnit3 + NSubstitute + ExpectedObjects) for unit tests and `dotnet-integration-test-skill` (Testcontainers / WebApplicationFactory) for repository/API tests — `ChoicePie.Backend.WebApi.Tests` is the current example, using `CustomWebApplicationFactory` + `Testcontainers.PostgreSql` for end-to-end HTTP auth-endpoint tests.

### Conventions that aren't obvious from a single file

- **Multi-node safe by default.** Startup migration + seeding run inside a Postgres advisory lock (`Database.AcquireAdvisoryLockAsync`) so concurrently starting nodes queue instead of colliding. Rate-limiter counters live in Redis (`RedisFixedWindowRateLimiter`, atomic Lua INCR + PEXPIRE) so limits hold across nodes; if Redis errors or takes >500ms the limiter falls back to an in-memory per-node window instead of failing requests. `MultiNodeGameHubTests` runs two `CustomWebApplicationFactory` nodes on shared containers.
- **Concurrent writes are guarded, never assumed away.** `EfUnitOfWork.SaveChangesAsync` turns `DbUpdateConcurrencyException` into `ConcurrencyConflictException` and Postgres unique violations into `UniqueConstraintViolationException` (both Shared.Kernel `DomainException`s → 409), so a "check-then-insert" handler relies on a DB unique index and catches the latter to answer idempotently or with its own exception (`RegisterMember`, `AddQuizFavorite`, `AddCreatorFollow`, `CreateQuizReport`, `StartQuizAttempt`). Single-use rows (`RefreshToken`, `PasswordResetToken`, `EmailVerificationToken`, `QuizAttempt`) use `UseXminConcurrencyToken()` and their handlers map the conflict to "token invalid" / "already completed" — except `RefreshToken` rotation, which has a 30s grace period for parallel SSR refreshes: on conflict `RefreshTokenCommandHandler` reloads the token (`IRefreshTokenRepository.ReloadAsync`) and still issues a new one if it was just rotated, rejecting only if it was logged out or the grace period passed, so the outcome doesn't depend on request timing. Counters never read-modify-write the aggregate: `IQuizRepository.IncrementShareCountAsync`/`RecordChallengeOutcomeAsync` are single atomic `ExecuteUpdate`s. AI generation allows one in-flight request per member (`IDistributedLock.TryAcquireAsync`, 409 `AiGenerationInProgressException`) because the quota is checked before, and recorded after, the slow AI call. `ConcurrencyTests` fires parallel requests against real Postgres to prove each case.
- **DI is by marker interface, not manual registration.** Implement `IScopedDependency`, `ITransientDependency`, or `ISingletonDependency` (Shared.Kernel) and Scrutor registers the class `AsSelfWithInterfaces` via the `AddApplication`/`AddDomain`/`AddInfrastructure` calls in `Program.cs`. Only cross-cutting services (e.g. `ICachingService`, `IUnitOfWork`) are registered explicitly in the Shared extension methods.
- **Domain events: two delivery modes, chosen per handler.** Aggregates call `AddDomainEvent(...)` (every event carries `EventId`/`OccurredOn` from `BaseDomainEvent`); `EfUnitOfWork.SaveChangesAsync` drains them and:
  - **In-process, immediately after commit** — publishes `DomainEventNotification<TEvent>` through MediatR. Best effort (lost if the process dies right after commit, one throwing handler stops the rest and surfaces as a 500 on an already-committed request). Use for things that must take effect before the response returns and are harmless to lose: cache invalidation, logging.
  - **Reliable, via Transactional Outbox** (`Shared.Infrastructure.Persistence/Outbox/`) — if any handler implements `INotificationHandler<ReliableDomainEventNotification<TEvent>>`, the event is written to `outbox_messages` **in the same transaction** as the business data (payload JSON encrypted with Data Protection — email events carry raw tokens; the key ring is shared via Redis `ChoicePie:DataProtection-Keys` so any node can decrypt). `OutboxProcessor` (hosted service on every node) claims batches with `FOR UPDATE SKIP LOCKED` + a 5-min lease, runs each handler in its own DI scope, records per-handler completion so retries only re-run the failed ones, backs off exponentially (10s → 1h cap), dead-letters after 10 attempts (`dead_lettered_at`, logged as error), and deletes the row on success. Delivery is **at-least-once with a ~1s delay** — handlers must be idempotent. Currently reliable: account emails (`SendPasswordResetEmailHandler`, `SendEmailVerificationEmailHandler`), `ArchivePublishedQuizzesOnAccountClosedHandler`, `RecordChallengeOutcomeHandler`.
  - Which events go to the outbox is decided at startup by `OutboxEventRegistry` scanning the assembly passed to `AddSharedPersistence<TContext>(...)` (the Application assembly). Any DbContext used with `EfUnitOfWork` must call `modelBuilder.ApplyOutboxConfiguration()`. When adding a reliable handler, add a sample of its event to `Infrastructure.Tests/Persistence/Outbox/ReliableEventContractTests` (it fails until you do) so the JSON round-trip is proven. Integration tests asserting a reliable handler's effect must `await factory.WaitForOutboxDrainedAsync()` first.
- **Repositories are subclasses, not a registered generic.** Derive from `EfGenericRepository<TEntity, TContext>`, implement `GetByIdAsync`, and override `ApplyInclude` for eager loading. Mark the subclass with a DI marker interface to register it. Each aggregate owns a per-aggregate repository interface in its Domain folder (e.g. `IMemberRepository : IRepository<Member>`) rather than Application code depending on `IRepository<T>` directly; filtered queries go through named `ISpecification<T>`/`Specification<T>` classes owned by the aggregate (e.g. `MemberByEmailSpecification`) instead of inline `Expression<Func<T,bool>>` predicates.
- **Repositories are command-only.** `IRepository<T>`/per-aggregate repositories (`IMemberRepository`, `IAuthAccountRepository`, ...) are injected only into MediatR *command* handlers, which need a tracked aggregate to mutate.
- **Query handlers depend on a per-feature Query Service, never on `IReadRepository` directly.** Mirrors the write-side rule (no generic repository injected straight into Application code): each feature owns an `I<X>QueryService` contract in `Application/<Feature>/Contracts/` (e.g. `IQuizQueryService`, `IMemberQueryService`), consumed by that feature's MediatR Query handlers. The MediatR Query handler stays thin: resolve the current-user/request context if needed, call the Query Service, return or propagate its result — no `IQueryable`/projection code belongs in a handler, and `Application` never references `IReadRepository`.
- **Query Service implementations live in `Infrastructure`, not `Application`.** The concrete class (e.g. `Infrastructure/QueryServices/Quizzes/QuizQueryService.cs : IQuizQueryService, IScopedDependency`) is the only thing that injects `IReadRepository` and projects straight into the response DTO with `.Select(...)`/LINQ joins (e.g. `readRepository.Query<Member>().Select(m => new MemberDto(...))`) — never call `Query<T>().ToList()`/materialize the full entity and map in C# afterward, that defeats the point of projection. This keeps `IQueryable`/EF-translatability concerns (e.g. `[NotMapped]` computed properties like `Quiz.OwnerId`/`Quiz.QuestionCount` aren't translatable — project through the underlying mapped property, `CreatorId`/`Questions.Count`, instead) out of Application entirely. Prefer a LINQ `join`/`GroupJoin`+`DefaultIfEmpty()` (LEFT JOIN) in one query over separate round-trips when the second aggregate's absence isn't itself an error (e.g. Quiz's creator falls back to "Unknown", never throws). Only fall back to separate projected queries per aggregate, combined in C#, when you need to tell "aggregate A not found" apart from "aggregate B not found" for distinct error handling (e.g. `MemberQueryService`: `MemberNotFoundException` vs `AuthAccountNotFoundException`) — a single JOIN can't make that distinction.
- **`IReadRepository` lives in `Shared.Infrastructure.Persistence/Repositories/IReadRepository.cs`, not Shared.Application.** It's not a cross-layer port (nothing in `Application` references it, only `Infrastructure` Query Services do) — it exists purely as a testability seam so Query Services can be unit-tested by mocking `Query<T>()` with an in-memory `List<T>().AsQueryable()` instead of needing a real Postgres/EF InMemory-provider integration test. Its concrete implementation is `Infrastructure/Persistence/Repositories/ReadRepository.cs : EfGenericReadRepository<ChoicePieDbContext>, IReadRepository, IScopedDependency` — one shared class for every aggregate (unlike write repositories, `EfGenericReadRepository<TContext>`'s `Query<T>()` is already generic per-call, so it doesn't need a subclass per aggregate). Query Service unit tests live in `ChoicePie.Backend.Infrastructure.Tests` (NUnit3 + NSubstitute, same as `Application.Tests`/`Domain.Tests`).
- **Aggregate folder layout**: `Domain/Aggregates/<Name>/` holds the aggregate root class directly (e.g. `Aggregates/Member/Member.cs`, `Aggregates/Quiz/Quiz.cs`), plus `Events/`, `Exceptions/`, `Specifications/`, and `Enums/` (for `Enumeration<T>` types owned by that aggregate) subfolders, and an `Entities/` subfolder reserved for that aggregate's *non-root* child entities only (empty/absent if the aggregate has none). Value objects shared across aggregates live in `Shared.Kernel/ValueObjects/`, not under any one aggregate.
- **Quiz read caching is a decorator, not a MediatR behavior.** `Infrastructure/Caching/Quizzes/CachedQuizQueryService` wraps `IQuizQueryService` (registered with Scrutor `.Decorate<,>()` in `Program.cs` — it must not carry a DI marker interface) and caches only caller-independent data: `GetByIdAsync`/`GetForAttemptAsync`/`GetRelatedAsync` (5 min) and `GetTagsAsync` (10 min). Per-user shaping (e.g. stripping Questions for non-owners) stays in the Query handlers, so cached DTOs are always complete and `[ImmutableObject(true)]` (use `with`, never mutate). Keys/tags live in `QuizCacheKeys` — bump the per-DTO version constant on incompatible DTO changes so rolling deploys don't read each other's entries. Invalidation is event-driven: `Quiz` raises `QuizDetailsUpdated`/`QuizCoverUpdated`/`QuizQuestionsChanged`/`QuizStatusChanged`, `Member` raises `MemberProfileChanged`, and `Application/Quizzes/EventHandlers/InvalidateQuizCacheHandlers` call the `IQuizCacheInvalidator` port (tag `quiz:{id}`; status/tag changes also clear `quiz-catalog`). Counters (`ChallengeCount`/`PassRate`/`ShareCount`) are intentionally not invalidated and go stale within the TTL. When adding a new mutation to `Quiz` that changes what these DTOs show, raise one of these events.
- **Persistence setup**: pooled `DbContext` (`AddSharedDbContextPool`) with snake_case naming (EFCore.NamingConventions). `ChoicePieDbContext` auto-applies all `IEntityTypeConfiguration` from the Infrastructure assembly — add entity configurations there.
- **Extension methods use the C# 14 `extension(...)` block syntax** (see `PersistenceServiceCollectionExtensions`); follow that style in new extension classes.
- Code comments and some exception messages are written in Traditional Chinese; keep that style when editing those files.
- **Never derive from the bare `Entity<TId>`.** All entities and aggregate roots — including child entities under `Entities/` — use `AuditableEntity<TId>` (or `AppendOnlyAuditableEntity` for append-only records) so audit columns and soft delete are always present. Treat `Entity<TId>` as legacy/unused; don't introduce new usages of it.
- **`[NotMapped]` computed properties (e.g. `Quiz.OwnerId => CreatorId!.Value`) must never appear inside a `Specification<T>` criteria lambda** — EF Core can't translate them to SQL, only the underlying mapped property (`CreatorId`) works there. `Specification<T>`'s constructor (`Shared.Kernel/Primitives/Specification.cs`) runs an `ExpressionVisitor` (`NotMappedMemberVisitor`) that throws `InvalidOperationException` immediately if the criteria references a `[NotMapped]` member, so this fails fast at construction — in a unit test, not silently in production against a real `IQueryable`. When adding a new computed alias property on an aggregate, mark it `[NotMapped]` (existing convention) so this guard actually catches misuse of it.
